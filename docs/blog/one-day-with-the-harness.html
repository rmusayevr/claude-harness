One Day With the Harness

A client questions tracker went from a list of GitHub issues to a finished v1 on a live staging site in one working day. An AI agent did the building and a second one reviewed it. This is what that looked like, including the mistakes, the stops, and the fixes the project forced back into the harness.

The loop

The owner wrote eleven issues, labelled them ready, and typed one command: /work-the-queue (/harness:work-the-queue if you installed the harness as a plugin). From there the agent repeated the same six steps for each issue, and added two issues of its own when it found work: local PostgreSQL, and a faster test suite. Nothing about the order is clever. What matters is that every step ends in something you can check on GitHub.

  1. 1
    Pick the next issue and size itSmall, Medium, or Risky. An issue that touches a risky path is Risky, and the agent never sizes down. Medium and Risky post a plan as an issue comment and wait for a person.
  2. 2
    Stop where a person has to decideThe project listed what only the owner may decide, such as who can see a project, or what client data leaves the system. Those issues stop at the plan.
  3. 3
    Build on a branch, with testsPer design-a-test every behaviour change gets a test, and a fix gets one that fails without it. Per verify-for-real each check passes by its own exit code.
  4. 4
    Read your own diff, then open the PRread-your-own-diff, then a PR into staging with Closes #n, and a description of what was verified and what was not.
  5. 5
    A reviewer with no memory reads the diffThe fresh-eyes-reviewer subagent has never seen the conversation that produced the code. triage-review labels each finding blocker, decision, settled or nit. Blockers get fixed. After three rounds it stops and asks.
  6. 6
    Merge when CI is green, then the next issueInto staging only. The loop never merges into main, and a hook refuses it.

The whole setup lives in one file in the project, .claude/harness-loop.json. This is the real one, trimmed to what the loop reads:

{
  "base": "staging",
  "protected": ["main"],
  "queue": { "label": "ready" },
  "checks": [
    "cd backend && python manage.py test --noinput",
    "cd frontend && npm run lint && npm run typecheck && npm test && npm run build"
  ],
  "risky": ["backend/accounts/", "migrations/", "backend/drafting/"],
  "stopFor": [
    "who can see or change a project",
    "anything that sends a message instead of drafting one",
    "what client data is sent to the drafting API"
  ]
}

One issue, start to finish: accounts

Issue #4 asked for sign-in and sign-out, with anonymous access to the API denied. It touches backend/accounts/, a risky path, so the plan waited for approval. The PR was open for 29 minutes, and review took three rounds and one decision from the owner.

The PR description carried the evidence: checks with exit codes, 20 backend tests and 11 frontend tests, and three mutation checks, where removing a protection (CSRF on login, the default permission class) makes a named test fail. Then an end-to-end run through the real proxy, which failed the first time. The path rewrite dropped a trailing slash, so every sign-in POST returned a 500 while every unit test passed. The fix and its regression test went into the same PR.

Review, round 1: four blockers

Round 2 produced a decision, not a fix

The fix for the forged header made every sign-in reach Django from the web server's own address. The throttle became one bucket for everybody, so ten bad attempts a minute from anyone would lock everyone out. The plan's rule, "10 per minute per IP", had no trustworthy IP behind a proxy.

decision The agent did not pick a rule. It asked the owner, who chose a throttle per account. Round 3 verified it through the real proxy: the tenth bad attempt on one email got a 400, the eleventh a 429, even with a forged header on every attempt, and another account signed in right after.

all day

What the fresh-eyes review caught

The reviewer found a real defect in most issues. These are the ones worth remembering, because none of them showed up in a green test run:

  • A deadlock the agent's own fix introduced (questions, #6). A row lock added to fix a race made two transactions wait on each other. Only a threaded test on real PostgreSQL showed it.
  • A refusal that showed nothing, and a lost update (question screens, #8). When the server refused an answer, the screen showed no message. Separately, two people editing the same question could silently overwrite each other.
  • An uncapped retry-after (drafting, #9). The API client would have waited as long as the server told it to.
  • A start command a visitor could keep down (deploy, #10). A rename by a visitor could have kept the service from starting.
  • A throttle bypass, a sign-out that lied, an email-case crash (accounts, #4), from the table above.

Every reviewer run is logged. The reviewer is read-only on git. On an earlier project a reviewer ran git checkout and left the shared checkout on a detached HEAD, so now it may only read, and anything it wants to run goes in a throwaway file outside the repo.

The plan for #9 listed five decisions with a recommended answer for each, and said plainly that it had not verified the account's data terms, because that is a fact about the account. It then waited. The deploy issue (#10) was parked the same way. The agent prepared everything in the repository, then waited for the owner to create the service in Render. The owner ran the smoke test against the live site: 12 checks, 12 passed.

fixes upstream

What the project taught the harness

The project was also the harness's first full test. Whenever the run hit a problem in the harness itself, the project session reported it and the fix went upstream, with a test, through the same issue loop. Three of the project's sixteen PRs are harness updates, and a fourth records two lessons.

What happenedWhat changed in the harness
A guard update took five review rounds. Each fix for a false alarm removed a block the old command splitter had caught by accident.Guards are never weaker than the plain split by construction, proved by a fuzz test of 8,000 generated commands and a replay of 6,359 real commands, none weaker (#11, #12 and #14).
Hundreds of chained evals made a guard run for 22 seconds against a 10 second hook limit. A hook that times out decides nothing.Capped the expansion. 5,000 chained evals now take under 10 ms, and a test pins eight extreme shapes.
The dependency review proposed packages released three to six days earlier.A release-age rule: pin the newest release at least two weeks old. The drafting feature got anthropic 2.3.0, not the 2.6.0 released three days before.
Only skills the loop named ever fired. The rest sat unused.The loop now names the skill at each step where it matters.
Reviews found real defects in most issues, and some skills guard data and secrets.The reviewer and five high-stakes skills are pinned to Opus, and pins only go up. A test stops anyone pinning a skill down, because a skill's model lasts for the rest of the turn.
/promote-lesson edits a skill, and the installer then skipped every later update to it.Updates merge recorded incidents only when that provably loses nothing. It took three fresh-eyes rounds to get right.
A lesson could reach the shared vault with a placeholder instead of a rule.--rule is now required on the first record.
Four large heredocs were refused with "unexpected EOF" and no guard decision.Tested and ruled out: the guards allow them in under 10 ms. The cause is not the hooks.

The honest part. Three of the harness's own changes (#6 to #8) were merged on a green CI run without a fresh-eyes review. A later review found the guards had become weaker. That is why "never weaker" is now a test, and why the riskier harness changes since then went through the same review the project's code gets.

8 to 11 minutes

What was slow

By issue #9 the backend test suite took between eight and eleven minutes (510 seconds at 146 tests, 683 at 233). The agent kept waiting on full runs, issue after issue, until the owner asked why it took so long.

Timing one unit explained it. On Windows, localhost tries the IPv6 address first. Nothing listened there, so each database connection waited 10.03 seconds against 0.06 seconds for 127.0.0.1. A suite of repeated connections multiplied it. Pointing the test servers at 127.0.0.1 took one group of tests from 130 seconds to 12.

Both findings were recorded as lessons in the project (localhost-ipv6-windows and time-one-unit-before-waiting), with the cost of each, so the next project does not repeat them.

the logs

What the logs say

The harness records which skills load, by name only and never the prompt, and every guard decision. Here is the project's usage log for the day:

  • 45 of 56 skills never fired. Most are for situations this app never had, such as debugging production, rollouts and incidents. A few the loop names, write-commit and scope-change among them, never fired either, and that is on the list to watch.
  • The guards made 10 decisions in total, all in the first third of the day: three denials of shell writes to .env, two of rm -rf on a broad path, one of a push to the base branch, and four asks. Some of those were the session's own probes of the guards. They made none during the last eleven PRs.
  • The skills that fired on their own were the ones whose moment came up: audit-permissions on accounts, migrate-data and review-for-data-loss on the questions table, review-a-dependency when drafting added a package.
your turn

Try it on your own project

You need Claude Code, the gh CLI signed in to GitHub, and a repository with CI.

  1. 1
    Install the harnessInside Claude Code:
    /plugin marketplace add rmusayevr/claude-harness
/plugin install harness@harness
    Or from a checkout: node install.mjs install --profile full --target your-project
  2. 2
    Ask it where to beginType /harness:start. It asks what you are doing and tells you what to say and what will happen.
  3. 3
    Write the loop fileCreate .claude/harness-loop.json like the one above: your base branch, the checks that must pass, the paths that are risky, and the things only a person may decide. Keep main protected.
  4. 4
    Write issues, label themOne clear outcome per issue, with a way to check it. Label them ready. The agent can also write an issue itself when it finds work, but only from a concrete finding.
  5. 5
    Run the loopType /harness:work-the-queue (/work-the-queue if you used the installer). Approve the plans it posts, answer its decisions, and say "merge" when you are satisfied. It will not merge into main.

Give it a small project first. Check the project's .claude/harness-usage.log after a week with npm run usage in the harness checkout, and delete what you never use.

What this does not show

  • One project, one day, one owner. The numbers say what happened, not what will happen to you.
  • No comparison. I did not measure how long the same app would take without the harness, so there is no "time saved" figure on this page.
  • The reviewer's false alarms were not counted. Its hit rate on real defects looks high, but a clean tally was not kept.
  • The harness was changing during the run. Some of the eleven and a half hours went to fixing the harness, and the fixes are in the harness repository, not in this tutorial.
  • Staging is live, but thin. It runs on free Render services with invented demo data. Drafting is not set up there (no Claude key), nobody has clicked through the screens on the live site, and nothing has been merged into main. No real client data has been used in the repository, the tests or the fixtures.
