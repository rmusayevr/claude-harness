One Project With the Harness

A client questions tracker went from a list of GitHub issues to a finished product on a live staging site, then into main. An AI agent did the building and a second one reviewed it. This page is about the whole project: how the loop works, one issue followed from start to finish, what review caught, where the agent stopped for a person, what the project forced back into the harness, and what the logs say once they are audited.

how it works

The loop

The owner started with eleven issues, labelled them ready, and typed one command: /work-the-queue (/harness:work-the-queue if you installed the harness as a plugin). From there the agent repeated the same six steps for each issue, and added issues of its own when it found work, such as local PostgreSQL and a faster test suite. By the end there were 53 issues and all of them were closed. Nothing about the order is clever. What matters is that every step ends in something you can check on GitHub.

  1. 1
    Pick the next issue and size itSmall, Medium, or Risky. An issue that touches a risky path is Risky, and the agent never sizes down. Medium and Risky post a plan as an issue comment and wait for a person.
  2. 2
    Stop where a person has to decideThe project listed what only the owner may decide, such as who can see a project, or what client data leaves the system. Those issues stop at the plan.
  3. 3
    Build on a branch, with testsPer design-a-test every behaviour change gets a test, and a fix gets one that fails without it. Per verify-for-real each check passes by its own exit code.
  4. 4
    Read your own diff, then open the PRread-your-own-diff, then a PR into staging with Closes #n, and a description of what was verified and what was not.
  5. 5
    A reviewer with no memory reads the diffThe fresh-eyes-reviewer subagent has never seen the conversation that produced the code. triage-review labels each finding blocker, decision, settled or nit. Blockers get fixed. After three rounds it stops and asks.
  6. 6
    Merge when CI is green, then the next issueInto staging only. The loop never merges into main, and a hook refuses it. The one release into main (#125) was its own pull request, made at the owner's instruction.

The whole setup lives in one file in the project, .claude/harness-loop.json. This is the real one at the end of the project:

{
  "base": "staging",
  "protected": ["main"],
  "queue": { "label": "ready", "parent": null },
  "parkedLabel": "waiting",
  "autoMerge": true,
  "mergeMethod": "merge",
  "checks": [
    "cd backend && python manage.py check",
    "cd backend && python manage.py makemigrations --check --dry-run",
    "cd backend && python manage.py test --noinput",
    "cd frontend && npm run lint && npm run typecheck && npm test && npm run build"
  ],
  "risky": ["backend/accounts/", "migrations/"],
  "stopFor": [
    "who can see or change a project",
    "anything that sends a message from the app"
  ]
}

On the first day the list of risky paths also held backend/drafting/ and the stop list named what client data goes to the drafting API. The drafting feature was removed later (#116), and the file shrank with it.

issue #4

One issue, start to finish: accounts

Issue #4 asked for sign-in and sign-out, with anonymous access to the API denied. It touches backend/accounts/, a risky path, so the plan waited for approval. The PR was open for 29 minutes, and review took three rounds and one decision from the owner.

The PR description carried the evidence: checks with exit codes, 20 backend tests and 11 frontend tests, and three mutation checks, where removing a protection (CSRF on login, the default permission class) makes a named test fail. Then an end-to-end run through the real proxy, which failed the first time. The path rewrite dropped a trailing slash, so every sign-in POST returned a 500 while every unit test passed. The fix and its regression test went into the same PR.

Review, round 1: four blockers

FindingLabelOutcome
The login throttle keyed on a client-controlled header, so a fresh header on each attempt never hit the limitblockerFixed, with a test that failed before (400 instead of 429)
A database migrated before the user model changed now fails migrateblockerREADME note; no deployed database exists yet
Sign-out showed "signed out" even when the backend refusedblockerFixed, test failed before the fix

Cookies are not marked SecurenitDeployment hardening, moved to the deploy issue

Round 2 produced a decision, not a fix

The fix for the forged header made every sign-in reach Django from the web server's own address. The throttle became one bucket for everybody, so ten bad attempts a minute from anyone would lock everyone out. The plan's rule, "10 per minute per IP", had no trustworthy IP behind a proxy.

decision The agent did not pick a rule. It asked the owner, who chose a throttle per account. Round 3 verified it through the real proxy: the tenth bad attempt on one email got a 400, the eleventh a 429, even with a forged header on every attempt, and another account signed in right after.

the reviewer

What the fresh-eyes review caught

65 of the 72 pull requests carry a review triage comment, and so do 51 of the 54 that touched backend or frontend code. The three code pull requests without one are #84, #93 and #125, the release. Where a triage ends in the status line triage-review prescribes, the project has 64 rounds. 8 of them ended not ready, and those lines report at least 126 blockers fixed. 15 of the 65 triage comments use another format and are not in that count. These are the catches worth remembering, because none of them showed up in a green test run:

  • A deadlock the agent's own fix introduced (questions, #6). A row lock added to fix a race made two transactions wait on each other. Only a threaded test on real PostgreSQL showed it.
  • A refusal that showed nothing, and a lost update (question screens, #8). When the server refused an answer, the screen showed no message. Separately, two people editing the same question could silently overwrite each other.
  • An uncapped retry-after (drafting, #9). The API client would have waited as long as the server told it to.
  • A start command a visitor could keep down (deploy, #10). A rename by a visitor could have kept the service from starting.
  • A throttle bypass, a sign-out that lied, an email-case crash (accounts, #4), from the table above.
  • A flag whose meaning was written from memory (#60). The agent wrote that -k is --keepdb in a comment, in the code and in the README. In Django's test runner it filters tests by name. The review caught it in round 1.
  • A test that passed with the lock removed (#117). A real-thread test for "at most 5 waiting answers" put its artificial delay before the count instead of between the count and the insert, so it stayed green without the lock. Mutation runs showed it, and the fix landed in the same pull request.

The one pull request merged without its review (#59, a per-process test database name) is covered under the logs. The review that ran afterwards found two regressions. The reviewer is read-only on git. On an earlier project a reviewer ran git checkout and left the shared checkout on a detached HEAD, so now it may only read, and anything it wants to run goes in a throwaway file outside the repo.

The owner ran the smoke test against the live site: 12 checks, 12 passed.

fixes upstream

What the project taught the harness

The project was also the harness's first full test. Whenever the run hit a problem in the harness itself, the project session reported it and the fix went upstream, with a test, through the same issue loop. Seven of the project's 72 pull requests touched only the .claude folder: harness updates and recorded lessons.

What happenedWhat changed in the harness
A guard update took five review rounds. Each fix for a false alarm removed a block the old command splitter had caught by accident.Guards are never weaker than the plain split by construction, proved by a fuzz test of 8,000 generated commands and a replay of 6,359 real commands, none weaker (#11, #12 and #14).
Hundreds of chained evals made a guard run for 22 seconds against a 10 second hook limit. A hook that times out decides nothing.Capped the expansion. 5,000 chained evals now take under 10 ms, and a test pins eight extreme shapes.
The dependency review proposed packages released three to six days earlier.A release-age rule: pin the newest release at least two weeks old. The drafting feature got anthropic 2.3.0, not the 2.6.0 released three days before.
Only skills the loop named ever fired. The rest sat unused.The loop now names the skill at each step where it matters.
Reviews found real defects, and some skills guard data and secrets.The reviewer and five high-stakes skills are pinned to Opus, and pins only go up. A test stops anyone pinning a skill down, because a skill's model lasts for the rest of the turn.
/promote-lesson edits a skill, and the installer then skipped every later update to it.Updates merge recorded incidents only when that provably loses nothing. It took three fresh-eyes rounds to get right.

A pull request was merged before its review ran (#59). The review afterwards found two regressions.The project added a hook that asks before merging a PR with no triage, and the harness now has it as guard-review-before-merge, a deny rather than an ask (see the logs below).
The project's guards asked 17 times about rm -rf, many of them for scratch folders the agent had just made.Scratch space the guard can prove from the command no longer asks. A variable is trusted only when every write to it is a plain assignment, which took two fresh-eyes rounds to get right.

Four large heredocs were refused with "unexpected EOF" and no guard decision.Tested and ruled out: the guards allow them in under 10 ms. The cause is not the hooks.

The honest part. Three of the harness's own changes (#6 to #8) were merged on a green CI run without a fresh-eyes review. A later review found the guards had become weaker. That is why "never weaker" is now a test, and why the riskier harness changes since then went through the same review the project's code gets.

8 to 11 minutes, then 25 seconds

What was slow

By issue #9 the backend test suite took between eight and eleven minutes (510 seconds at 146 tests, 683 at 233). The agent kept waiting on full runs, issue after issue, until the owner asked why it took so long.

Timing one unit explained it. On Windows, localhost tries the IPv6 address first. Nothing listened there, so each database connection waited 10.03 seconds against 0.06 seconds for 127.0.0.1. A suite of repeated connections multiplied it. Pointing the test servers at 127.0.0.1 took one group of tests from 130 seconds to 12.

Both findings were recorded as lessons in the project (localhost-ipv6-windows and time-one-unit-before-waiting), with the cost of each, so the next project does not repeat them. By the end the backend suite had grown to 512 tests, and the last CI run read "Ran 512 tests in 24.840s".

the logs

What the logs say

The harness records which skills load, by name only and never the prompt, and every guard decision. These are the project's logs for the whole run, 8 to 15 November, after removing the entries the hooks logged twice (explained below). The chart counts what the usage log recorded, and the reviewer bar is a minimum.

  • 16 of the harness's skills fired, and 40 of the 56 on disk never did. Most of those are for situations this app never had, such as debugging production, rollouts and incidents. The skills that fired on their own were the ones whose moment came up: audit-permissions on accounts, migrate-data and review-for-data-loss on the questions table, review-a-dependency when a package was added. The log has two sessions in it and misses the last days, so no skill was deleted on that evidence.
  • The guards made 62 decisions: 53 asks and 9 denials. 21 asks were before merging a PR with no triage (the project's own hook), 17 on rm -rf of something not on the regenerable list, 12 on wiping a data store, and 3 on a migration or production config. The denials were 6 shell writes to .env, 2 of rm -rf on a broad path, and 1 push to the base branch. 10 of the 62 came on the first day.
  • Many of the rm -rf asks were scratch folders the agent had just made, which is prompt fatigue, the thing the guard tests are written to prevent. That is fixed in the harness for the cases the guard can prove from the command. Several of the data-wipe asks were DROP DATABASE on scratch databases made in earlier commands. The guard cannot tell those from a real one without guessing at names, so it still asks. I did not count how many of the asks were mistakes; a guess would flatter the guards.
  • A review was skipped once, and a rule did not stop it. PR #59 merged before its fresh-eyes review ran, and the review afterwards found two regressions, fixed in #60 over two rounds. The project then added a hook that asks before merging a pull request with no review triage comment. It asked 21 times, always in auto mode, and the merges that followed went ahead. An ask that nobody answers is not a gate, so the harness version of that hook is a deny. It also showed that triage comments do not all follow one format, so the harness version looks for the status line the skill asks for.
  • The first counts were too high. The harness was installed in the project and also enabled as a plugin from 9 November, so every harness hook ran twice and logged twice. The decisions log held 86 entries that were 66 distinct decisions (62 once four test fixtures are removed), and the usage log held 94 reviewer entries that were 67 runs. I found this while writing the first version of this section, which used the inflated numbers. The plugin copy now stands down when the project has its own.
  • The reviewer is missing from the log after 12 November. The hook rejected a subagent called by its plugin-qualified name, so a reviewer launched that way was never recorded. That is the likely reason, since pull requests 113 to 124 have triage comments and the log has no reviewer after 12 November. I did not confirm how those later reviews were launched.
  • Ten lessons were recorded, and three say the rule already existed. A flag's meaning written from memory (the guidance against inventing flags was already in CLAUDE.md), a new endpoint breaking hand-built test mocks (the scope-change skill already says to check mocks), and slow runs waited on instead of timed (the profiling skill already says to measure). A written rule did not fire at the moment it was needed. That is the finding the harness has no good answer to yet.

The honest part. One project, one owner, and the same person ran the harness and wrote this up. The audit found the harness doing its job (reviews caught real defects, the .env guard denied six times) and also costing something: about thirty prompts around scratch folders and scratch databases, some of them avoidable. It did not find out whether the harness saved time.

your turn

Try it on your own project

You need Claude Code, the gh CLI signed in to GitHub, and a repository with CI.

  1. 1
    Install the harnessInside Claude Code:
    /plugin marketplace add rmusayevr/claude-harness
/plugin install harness@harness
    Or from a checkout: node install.mjs install --profile full --target your-project
  2. 2
    Ask it where to beginType /harness:start. It asks what you are doing and tells you what to say and what will happen.
  3. 3
    Write the loop fileCreate .claude/harness-loop.json like the one above: your base branch, the checks that must pass, the paths that are risky, and the things only a person may decide. Keep main protected.
  4. 4
    Write issues, label themOne clear outcome per issue, with a way to check it. Label them ready. The agent can also write an issue itself when it finds work, but only from a concrete finding.
  5. 5
    Run the loopType /harness:work-the-queue (/work-the-queue if you used the installer). Approve the plans it posts, answer its decisions, and say "merge" when you are satisfied. It will not merge into main.

Give it a small project first. Check the project's .claude/harness-usage.log after a week with npm run usage in the harness checkout, and delete what you never use.

What this does not show

  • One project, one owner. The numbers say what happened, not what will happen to you.
  • No comparison. I did not measure how long the same app would take without the harness, so there is no "time saved" figure on this page.
  • The reviewer's false alarms were not counted. Its hit rate on real defects looks high, but a clean tally was not kept.
  • The harness was changing during the run. Some of the work went to fixing the harness, and the fixes are in the harness repository, not in this tutorial. Some numbers from the project's logs were corrected after the hooks were found to log twice, and the reviewer count is still a minimum.
  • Staging is live, but thin. It runs on free Render services. The README of the project records that the owner clicked through the screens by hand on the staging site, and that no script has driven a browser since the headless runs. The release into main merged on 15 November. The sentence from the first-day write-up that no real client data was used in the repository, the tests or the fixtures was not re-checked for this update.
